BPRI.ExceptionHandling

Un paquet NuGet qui attrape les exceptions d'une API ASP.NET Core, renvoie une réponse JSON propre avec un TraceId, et enregistre les erreurs, les logs de l'application et (en option) les requêtes dans un fichier, SQL Server et par e-mail.

Vue d'ensemble

L'API n'a rien à savoir de Serilog. Elle appelle trois méthodes du paquet, lève des AppException quand une règle métier échoue, et utilise ILogger<T> comme d'habitude. Tout le reste (sinks, format, contexte, e-mail) est dans le paquet et se règle dans un fichier exceptionhandling.json.

Schéma de fonctionnement

Ce qui se passe pour une requête qui échoue

  1. Le middleware d'exceptions calcule le TraceId (celui de l'Activity en cours, sinon HttpContext.TraceIdentifier) et le place dans l'en-tête X-Trace-Id avant tout traitement.
  2. Le reste du pipeline lève une exception.
  3. MapException (code de l'API) est essayée en premier. Si elle renvoie null, MapDefault décide du statut et du message.
  4. L'exception est écrite avec un niveau selon le statut : 404 Information, autres 4xx Warning, 5xx Error. L'empreinte, le type, l'exception interne et le contexte sont ajoutés.
  5. Si la réponse n'a pas déjà commencé, le middleware écrit un ProblemDetails JSON avec le message convivial, le traceId et, pour la validation, la liste errors.
  6. Le tracing, s'il est actif, voit passer cette réponse d'erreur et l'enregistre avec sa durée.

Utilisation dans une API

1. Installer le paquet

dotnet add package BPRI.ExceptionHandling

Le projet référence Microsoft.AspNetCore.App : aucun autre paquet Serilog n'est nécessaire dans l'API.

2. Program.cs

var builder = WebApplication.CreateBuilder(args);

// 1) Charge exceptionhandling.json (obligatoire) puis exceptionhandling.{Environment}.json (optionnel)
builder.Configuration.AddBpriExceptionHandlingFile(builder.Environment);

// 2) Enregistre les services du paquet
builder.Services.AddBpriExceptionHandling(builder.Configuration, o =>
{
    // Facultatif : transformer une exception de votre code en réponse HTTP
    o.MapException = exception =>
    {
        if (exception is not ValidationException validation)
        {
            return null;                       // null = comportement par défaut du paquet
        }

        var errors = validation.Errors
            .GroupBy(e => e.PropertyName)
            .ToDictionary(g => g.Key, g => g.Select(e => e.ErrorMessage).ToArray());

        return new ErrorInfo(400, "Les données saisies sont invalides.", errors);
    };
});

var app = builder.Build();

// 3) Premier middleware du pipeline
app.UseBpriExceptionHandling();

app.UseSwagger();      // puis le reste : CORS, authentification, endpoints...
app.UseAuthentication();
app.UseAuthorization();
app.Run();

Ordre. UseBpriExceptionHandling() doit venir avant tout le reste. Il enregistre d'abord le tracing (s'il est actif) puis le middleware d'exceptions, donc le tracing enveloppe tout, y compris les réponses 401, 429 ou 500 produites plus loin.

3. Chaîne de connexion

Dans appsettings.json (pas dans exceptionhandling.json), sous le nom indiqué par Database:ConnectionStringName (ExceptionLogs par défaut) :

"ConnectionStrings": {
  "ExceptionLogs": "Server=.;Database=BpriLogsDb;Trusted_Connection=True;TrustServerCertificate=True;"
}

4. Dans le code métier

// Erreur métier : le message est renvoyé tel quel au client
throw new AppException("Ce produit existe déjà.", 409);

// Logs : ILogger classique, aucun type Serilog
public class CatalogueService
{
    private readonly ILogger<CatalogueService> _logger;
    public CatalogueService(ILogger<CatalogueService> logger) => _logger = logger;

    public void Exemple() => _logger.LogInformation("Catalogue créé");
}

5. Ce que reçoit le client

HTTP/1.1 409 Conflict
X-Trace-Id: 4bf92f3577b34da6a3ce929d0e0e4736
Content-Type: application/problem+json

{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.10",
  "title": "Ce produit existe déjà.",
  "status": 409,
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}

Les réponses de succès restent le DTO brut. Le champ type est ajouté par ASP.NET Core et pointe vers la définition du code HTTP dans la RFC 9110.

Batch, service ou application console

Le paquet fonctionne avec un host .NET (Host.CreateApplicationBuilder ou Worker Service). Il n'y a pas de middleware : on injecte IExceptionReporter et on appelle Report dans les catch.

var builder = Host.CreateApplicationBuilder(args);
builder.Configuration.AddBpriExceptionHandlingFile(builder.Environment);
builder.Services.AddBpriExceptionHandling(builder.Configuration);
builder.Services.AddHostedService<MonBatch>();

using var host = builder.Build();   // la libération du host envoie les derniers logs en base
await host.RunAsync();

public class MonBatch(IExceptionReporter reporter, ILogger<MonBatch> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken token)
    {
        try
        {
            logger.LogInformation("Début du traitement");
        }
        catch (Exception ex)
        {
            reporter.Report(ex);   // fichier + SQL Server + e-mail, comme dans une API
        }
    }
}

Libérer le host avant de quitter (using var host ou StopAsync) : les lots SQL partent toutes les 2 secondes, les derniers logs seraient perdus sinon. Utiliser des chemins absolus dans File:Path et copier exceptionhandling.json dans le dossier de sortie. Le paquet référence encore le framework ASP.NET, qui doit être présent sur le serveur d'exécution.

Pourquoi ILogger dans l'API et pas Serilog

L'API écrit ses logs avec l'abstraction de Microsoft. Le paquet branche ensuite son propre ILoggerProvider sur cette abstraction, qui transmet chaque message à son Serilog interne. L'API garde ainsi un seul type de logger, et le paquet peut changer de moteur sans toucher aux projets qui l'utilisent.

Ce que l'on gagne avec ILogger

  • L'API et la couche Application dépendent uniquement de Microsoft.Extensions.Logging : aucun paquet Serilog à installer ou à mettre à jour dans chaque projet.
  • Le contexte (cprj, utilisateur, TraceId) est ajouté automatiquement par le paquet, sans code dans les services.
  • Les niveaux se règlent dans exceptionhandling.json : ApplicationLogs:MinimumLevel pour votre code, FrameworkMinimumLevel pour Microsoft.* et System.*.
  • Les services restent testables avec n'importe quel faux ILogger.

Pourquoi Serilog reste dans le paquet

  • Ce sont ses sinks (fichier, SQL Server, e-mail) qui font le travail d'écriture.
  • Le logger du paquet est indépendant de celui de l'application : un projet qui utilise déjà son propre Serilog n'est pas perturbé.
  • Le type ILogger<CatalogueService> vient bien de Microsoft, mais le message finit dans Serilog via ApplicationLogProvider.

Validation au démarrage

AddBpriExceptionHandling refuse de démarrer avec une configuration incohérente : base activée sans chaîne de connexion, ApplicationLogs sans base, RequestTracing sans fichier ni base, e-mail sans Host, From ou To. Le message d'erreur nomme la clé à corriger.

Fichier par fichier

Dossier src/BPRI.ExceptionHandling. Les types marqués internal ne sont pas visibles de l'API.

BPRI.ExceptionHandling.csproj

Définition du paquet.
  • Cible net9.0, nullable et usings implicites activés, version 2.0.0, README inclus dans le paquet.
  • FrameworkReference Microsoft.AspNetCore.App donne accès à HTTP et à ILoggerProvider sans paquet supplémentaire.
  • Dépendances : Serilog 4, Sinks.File 7.0.0, Sinks.MSSqlServer 8, Sinks.Email 4, Formatting.Compact 3.
  • Templates/ErrorMail.html est une ressource intégrée à l'assembly.

Exceptions/AppException.cs

Types publics utilisés par l'API.
  • record ErrorInfo(int StatusCode, string Message, IReadOnlyDictionary<string, string[]>? Errors = null) : la réponse décidée pour une exception. Errors sert à la validation (champ vers messages).
  • class AppException : Exception : exception métier. Constructeur (string message, int statusCode = 400, Exception? inner = null). Propriété StatusCode. Son message est renvoyé tel quel au client.

Extensions/ExceptionHandlerExtensions.cs

Point d'entrée : les trois méthodes appelées depuis Program.cs.
  • AddBpriExceptionHandlingFile(this IConfigurationBuilder, IHostEnvironment, string fileName = "exceptionhandling") : ajoute exceptionhandling.json (obligatoire) et exceptionhandling.{Environment}.json (optionnel), sans rechargement à chaud.
  • AddBpriExceptionHandling(this IServiceCollection, IConfiguration, Action<ExceptionHandlingOptions>? configure = null) : lit la section, applique configure, complète la chaîne de connexion depuis ConnectionStrings, valide, puis enregistre en singletons : IHttpContextAccessor, les options, RequestContextEnricher, ExceptionLogger, IExceptionReporter, RequestTraceLogger (si le tracing est actif) et ApplicationLogProvider comme ILoggerProvider (si ApplicationLogs est actif).
  • UseBpriExceptionHandling(this IApplicationBuilder) : récupère les services, ajoute RequestTracingMiddleware si le tracing est actif, puis ExceptionHandlingMiddleware. À placer en premier.
  • Validate(options) (privée) : lève InvalidOperationException pour toute combinaison incohérente décrite plus haut.

Options/ExceptionHandlingOptions.cs

Toute la configuration, sous forme de classes liées à la section ExceptionHandling.
  • ExceptionHandlingOptions : racine (SectionName = "ExceptionHandling"), propriétés générales, sous-sections, et les deux délégués MapException et WriteResponse.
  • ContextOptions, ApplicationLogsOptions, FileLogOptions, DatabaseLogOptions, EmailLogOptions : une classe par sous-section, avec les valeurs par défaut décrites dans le chapitre Configuration.
  • RequestTracingOptions et RequestTraceDatabaseOptions : réglages du tracing. Son File démarre avec logs/requests-.log et Json = true.

Middleware/ExceptionHandlingMiddleware.cs (internal)

Attrape les exceptions et écrit la réponse.
  • InvokeAsync(HttpContext) : pose l'en-tête TraceId, appelle la suite dans un try. Une annulation due à la déconnexion du client donne un statut 499 sans log. Toute autre exception est mappée, loggée, puis écrite. Si la réponse a déjà commencé, l'exception est relancée.
  • MapDefault(Exception) : AppException avec son statut et son message, KeyNotFoundException 404, UnauthorizedAccessException 401, ArgumentException ou FormatException 400, tout le reste 500 avec UserFriendlyMessage.
  • WriteProblem(...) : ProblemDetails avec title (message), status, traceId et errors si présent.

Middleware/RequestTracingMiddleware.cs (internal)

Trace chaque requête : entrée, réponse, durée. Actif seulement si RequestTracing:Enabled.
  • Constructeur : fixe les méthodes tracées et compile deux expressions régulières de masquage, une pour le JSON ("champ": "valeur") et une pour les formulaires et query strings (champ=valeur).
  • InvokeAsync : si la requête n'est pas concernée, passe son chemin. Sinon lit le corps de la requête, remplace le flux de réponse par un MemoryStream, appelle la suite, puis dans le finally arrête le chronomètre, masque la query string, appelle RequestTraceLogger.Write, et recopie la réponse vers le vrai flux.
  • ShouldTrace : méthode dans la liste et chemin hors de ExcludedPaths.
  • ReadRequestBodyAsync : renvoie null sans corps, un texte de remplacement si le contenu n'est pas du texte ou dépasse 1 Mo, sinon lit avec EnableBuffering et remet le flux au début pour que l'endpoint puisse relire.
  • ReadResponseBody : texte de remplacement pour un contenu compressé ou non textuel.
  • Clean : masque les valeurs sensibles puis tronque à MaxBodyLength. IsText accepte json, text, xml et x-www-form-urlencoded.

Services/RequestContextEnricher.cs (internal)

Ajoute le contexte de la requête en cours à chaque log, de n'importe quel logger du paquet.
  • TraceId(HttpContext?) (statique) : Activity.Current.TraceId sinon TraceIdentifier. Utilisé aussi par le middleware pour l'en-tête.
  • Enrich(LogEvent, factory) : ajoute ApplicationName, EnvironmentName, MachineName, Cprj, TraceId, puis, s'il y a une requête, HttpMethod, Path, UserName, UserId et Claims. Une propriété déjà présente n'est pas écrasée.
  • ResolveCprj : claim JWT, en-tête, cprj de la config, nom de l'application.
  • LoggedClaims : sérialise en JSON les claims demandés si l'utilisateur est authentifié. Values tient compte des alias que .NET applique aux JWT (sub devient NameIdentifier, email, role…).

Services/ExceptionLogger.cs (internal)

Le Serilog des exceptions et des logs ILogger. Niveau minimum Verbose, filtrage par sink.
  • Constructeur : active l'auto-diagnostic Serilog (erreurs de sink écrites sur la console), ajoute l'enricher, puis les sinks activés.
  • LevelFor(int statusCode) : 404 Information, autres 4xx Warning, 5xx Error. Partagé par le middleware et ExceptionReporter.
  • Write(LogEventLevel, Exception, int statusCode) : appelé par le middleware et par ExceptionReporter. Ajoute StatusCode, ExceptionType, InnerException et Fingerprint.
  • ForCategory(string) : logger Serilog avec SourceContext pour une catégorie ILogger. Utilisé par ApplicationLogProvider.
  • AddFileSink : texte (modèle fixe) ou JSON (JsonFormat), rotation quotidienne, fichier partagé.
  • AddDatabaseSink : sink SQL Server par lots de 50 ou toutes les 2 s, création de la table et éventuellement de la base. BuildColumns définit les colonnes (voir Tables SQL).
  • AddEmailSink : sous-logger filtré par IsException, avec regroupement et corps HTML via HtmlEmailFormatter.
  • JsonFormat(FileLogOptions) : CompactJsonFormatter si Compact, sinon JsonFormatter. Partagé avec le tracing.
  • Fingerprint : SHA-256 de « type | première ligne de la stack », 8 octets en hexadécimal. Deux occurrences de la même erreur ont la même empreinte.
  • CreateDatabaseIfMissing : se connecte à master et crée la base. Une erreur est écrite sur la console, sans arrêter l'application.
  • Dispose : vide les tampons du logger.

Services/ApplicationLogProvider.cs (internal)

Le pont entre ILogger de Microsoft et Serilog.
  • CreateLogger(string categoryName) : choisit le niveau minimum (FrameworkMinimumLevel pour les catégories Microsoft. et System., sinon MinimumLevel) et renvoie un Bridge.
  • Bridge.IsEnabled : le niveau doit atteindre le minimum. Bridge.Log : formate le message avec le formatter de Microsoft puis l'écrit en Serilog avec l'exception éventuelle. BeginScope ne fait rien.
  • ToSerilogLevel : Trace Verbose, Debug Debug, Information Information, Warning Warning, Error Error, Critical Fatal.

Services/ExceptionReporter.cs

Écriture d'une exception hors HTTP (batch, console).
  • interface IExceptionReporter (publique) : Report(Exception exception, int statusCode = 500). Enregistrée par AddBpriExceptionHandling.
  • ExceptionReporter (internal) : appelle ExceptionLogger.Write avec le niveau donné par ExceptionLogger.LevelFor(statusCode), le même calcul que le middleware.

Services/RequestTraceLogger.cs (internal)

Un second Serilog, réservé au tracing, séparé des logs d'exceptions.
  • Constructeur : sink fichier et/ou table selon RequestTracing, avec le même enricher.
  • Write(method, path, query, statusCode, durationMs, requestBody, responseBody) : niveau Error pour un 5xx, Warning pour un 4xx, Information sinon. Ajoute QueryString, StatusCode, DurationMs, les deux corps, et UserName = "anonymous" quand aucun utilisateur n'est connecté.
  • AddFileSink (texte avec IN / OUT ou JSON), AddDatabaseSink et BuildColumns : mêmes principes que ExceptionLogger, sans colonne Exception.

Services/HtmlEmailFormatter.cs (internal)

Fabrique le corps HTML de l'e-mail d'erreur.
  • Constructeur : charge le modèle indiqué par TemplatePath, sinon la ressource ErrorMail.html.
  • Format(LogEvent, TextWriter) : remplace chaque {{Variable}} par la valeur correspondante, encodée en HTML. {{Color}} est rouge pour Error, orange pour Warning, bleu sinon.
  • GetProperty lit une propriété du log, ReadDefaultTemplate lit la ressource intégrée.

Templates/ErrorMail.html

Modèle par défaut de l'e-mail : bandeau coloré avec le type et le statut, tableau application / cprj / TraceId / requête / utilisateur / environnement, puis la stack trace.

Points d'attention

Mot de passe SMTP. Il ne doit pas rester en clair dans exceptionhandling.json. Utiliser dotnet user-secrets set "ExceptionHandling:Email:Password" "..." en développement ou une variable d'environnement ExceptionHandling__Email__Password en production, et changer le mot de passe déjà partagé.

Données personnelles dans le tracing. Les corps de requêtes et de réponses sont enregistrés. Les mots de passe et jetons sont masqués, pas les autres champs. Activer RequestTracing en connaissance de cause, exclure les chemins sensibles avec ExcludedPaths et ajouter les champs propres à l'application dans MaskedFields.

Logs ILogger dans le fichier. L'option ApplicationLogs est décrite comme « uniquement en base », mais dans le code seul le sink e-mail est filtré sur les exceptions. Le sink fichier reçoit donc aussi les logs ILogger. Si le fichier ne doit contenir que les exceptions, il faut ajouter le même filtre IsException au sink fichier.

Tracing et mémoire. La réponse est mise en mémoire avant d'être envoyée, pour pouvoir en lire le corps. À éviter pour des téléchargements volumineux : exclure ces chemins avec ExcludedPaths. Les corps de requête de plus de 1 Mo ne sont pas lus.

Cprj dans le JWT. Pour que chaque log porte le bon cprj, l'API qui émet les jetons doit y ajouter la claim cprj. Sans elle, le cprj de la configuration est utilisé (CatalogueAPP pour Catalog.Api).
